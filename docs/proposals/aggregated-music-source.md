# 聚合音乐源（类洛雪自定义源）可行性方案

> 状态：提案，未实施。来源：issue #102「可以支持添加聚合音乐源吗，类似洛雪那种」。

## 1. 需求理解

用户期望在现有网易云、QQ 音乐、酷狗之外，能接入"聚合源"，使这三个平台拿不到播放链接（VIP、无版权）的歌曲仍可播放。洛雪的做法是：用户导入第三方编写的 JavaScript 源脚本，脚本负责把"歌曲信息"换成"可播放的 HTTP 链接"。

这里实际有两种不同的诉求，方案差别很大：

| 诉求 | 含义 | 洛雪是否如此 |
|---|---|---|
| A. 多一个**取链来源** | 搜索、歌单仍来自现有三平台，只在取不到链接时，换一个渠道取链接 | 是。洛雪自身不提供音频，只把歌名、歌手交给"源"，由源返回链接 |
| B. 多一个**完整音乐平台** | 新平台有自己的搜索、歌单、歌词、封面、登录 | 否 |

洛雪的自定义源接口本质是 A：`musicUrl`（取链）加可选的 `lyric`、`pic`，搜索不经过源。下面以 A 为主评估，B 单独说明。

## 2. 洛雪自定义源的实际机制（已核对官方文档）

- 脚本是单个 JS 文件，头部注释声明 `@name` 等元信息。
- 脚本通过 `globalThis.lx` 与宿主交互：`lx.on('request', handler)` 接收取链请求，`lx.send('inited', { sources })` 声明支持的源（`kw/kg/tx/wy/mg/local`）与音质（`128k / 320k / flac / flac24bit`）。
- 宿主给脚本提供 `lx.request`（不受跨域限制的 HTTP 请求）、`lx.utils`（`md5`、`aes`、`rsa`、`zlib`、`Buffer`）。
- `request` 的入参是洛雪自己的 `musicInfo`（含 `songmid`、`hash` 等洛雪内部字段），出参是 URL 字符串。
- 桌面版文档的许可：项目 Apache-2.0，另附"许可协议"补充条款（见第 5 节）。

关键结论：脚本能做的事是"发任意 HTTP 请求并返回一个 URL"，没有文件、进程能力，但 `lx.request` 本身就是一个能请求任意地址的出口。完整兼容的实际约束见第 10 节（已读取洛雪桌面版运行时源码）。

## 3. 与本项目现状的差距

| 方面 | 现状 | 对聚合源的影响 |
|---|---|---|
| 来源类型 | `MusicSource = 'netease' \| 'tencent' \| 'kugou'`，`shared/types.ts:25` | 方案 A 不必改它（见方案 1）；方案 B 必须改 |
| 硬编码分支 | `'netease'` 54 处/26 文件、`'tencent'` 37 处/17 文件、`'kugou'` 33 处/13 文件 | 方案 B 的主要成本 |
| 取链入口 | `musicProvider.getStreamUrl(source, urlId, bitrate, cookie)`，`resolveStreamUrl` 带音质降级 | 方案 A 的天然插入点 |
| 链接校验 | `mediaSourceRequest.validateMediaUrl`：只允许 https、无端口，且主机必须在该平台自己的 CDN 后缀内（`music.126.net`、`tc.qq.com`、`kugou.com`） | **聚合源返回的链接会全部被拒**。这是小程序音频代理的 SSRF 防线，不能直接放开 |
| 网页端播放 | 客户端 Howler 直接用 `streamUrl` 播放 | 网页端不经过上面的校验，但受浏览器混合内容、CORS、防盗链影响 |
| 自动降级 | `trackFallbackService` 只在网易云与 QQ 之间换源，按标题、歌手、时长打分匹配 | 已有"拿不到就换渠道"的雏形，可扩展 |
| 执行不受信任代码 | 服务端目前没有任何先例 | 方案 2 需要新建沙箱，是最大风险 |
| 管理员配置 | 服务端只有环境变量（`MAPP_*`、`autoFallback` 等） | 适合作为聚合源的开关与配置入口 |

## 4. 方案

### 方案 0：不做（回复 issue）

说明取舍：版权、安全、维护成本。零成本，但不满足诉求。

### 方案 1：服务端配置的"备用取链渠道"（推荐起点）

**思路**：不做脚本、不改 `MusicSource`。在服务端增加一个可选的"取链回退渠道"：当三个平台取不到链接时，把歌曲的标题、歌手、时长交给管理员配置的渠道，换回一个链接。

渠道的形态选 **HTTP 接口**，而不是脚本：

- 管理员在环境变量里配置一个或多个渠道，例如 `FALLBACK_SOURCES=[{"name":"x","url":"https://…/url","timeoutMs":5000}]`。
- 服务端向渠道发一个固定格式的请求（歌曲名、歌手、时长、期望音质），渠道返回 `{ url }`。
- 返回的 URL 经过校验后写入 `Track.streamUrl`；`Track.source` 保持原平台，列表、封面、歌词不变。

**要改的地方**

| 位置 | 改动 |
|---|---|
| `server/config.ts` | 新增渠道配置的 schema 与校验，默认关闭 |
| 新增 `services/externalUrlResolver.ts` | 向渠道取链，带超时、响应大小限制、业务码校验 |
| `streamUrlResolver.ts` / `playerService._playTrackInRoom` | 平台取链失败后，沿用现有"自动降级"位置再试渠道 |
| `mediaSourceRequest.validateMediaUrl` | 新增"渠道链接"的校验策略（见下） |
| 客户端 | 只需在降级 toast 里区分"已使用备用渠道"，无需新增页面 |
| 测试与文档 | 渠道响应用 fixture mock；更新 `design-patterns.md`、`deployment.md` |

**优点**：改动局限在服务端取链路径，不碰类型系统和 UI；不执行不受信任的代码；由部署者而非房间用户决定接入什么，责任清晰；可以用一个小适配器接入洛雪生态里已有的 HTTP 化源服务。

**局限**：用户不能自己导入脚本；只解决"取链"，不解决搜索。

### 方案 2：内置洛雪脚本运行时（不推荐；完整分析见第 10 节）

**思路**：兼容洛雪的 `globalThis.lx` 接口，让部署者导入现成的洛雪源脚本，由服务端沙箱执行。

**需要做的**

1. 选定沙箱：`isolated-vm`（V8 isolate，需要原生编译，Docker alpine 要额外依赖）、`quickjs-emscripten`（WASM，较轻，性能较低）或独立子进程加权限限制。
2. 实现 `lx.request`：必须走带 SSRF 防护的出口（现有 `pinnedLookup` 和 `isPublicMediaAddress` 可复用），限制目标、次数、响应大小、总耗时。
3. 实现 `lx.utils`：`md5`、`aes`、`rsa`、`zlib`、`Buffer`。
4. 把本项目的 `Track` 映射成洛雪的 `musicInfo`。脚本依赖 `songmid`、`hash` 等洛雪专用字段，而我们的 `Track` 里没有这些，只能按"来源平台"尽力构造，有些源会取不到。
5. 脚本的导入、版本、更新提示、启停管理，以及脚本崩溃、死循环、内存超限的处理。
6. 安全评审：脚本能让服务器去请求任意地址（即使过滤了内网，也能把服务器变成代理），也能读到传入的 Cookie（若把用户登录 Cookie 传给脚本，则泄露风险极高，必须不传）。

**风险**：

- 这是本项目第一次在服务端运行第三方代码，攻击面远大于其他所有功能；
- 兼容性不可保证：洛雪的 API 有版本，且脚本多是混淆过的，行为不可审计；
- 维护成本持续存在。

### 方案 3：完整新增一个"聚合"平台（方案 B，不推荐）

把聚合源做成第四个 `MusicSource`，拥有搜索、歌单、歌词、封面。需要改 `MusicSource` 类型及约 100 处硬编码分支、客户端各平台 UI、`Track.id` 映射，并且聚合源本身没有统一的搜索接口，需要另找后端。成本是方案 1 的数倍，且依赖外部服务的稳定性，不建议。

## 5. 法律与合规

这是比技术更需要先判断的部分：

- 本项目是 AGPL-3.0，运行在服务器上，**服务器会成为音频流的中转与分发方**。小程序路径尤其如此：音频由服务端代理（`platformMediaService`）转发给用户。
- 洛雪的许可协议明确声明：项目自身没有获取音频的能力，音频来自第三方源；要求使用者 24 小时内清除版权数据；"仅用于技术可行性探索，禁止违法使用"。它把责任转给使用者，**而本项目是多人共享的服务端部署，责任主体不再是单个最终用户**。
- 现有三个平台走的是各平台公开接口，用户用自己的账号登录取 VIP 链接。聚合源则可能绕过平台的付费与版权限制，性质不同。
- 本仓库的 README、SECURITY 目前没有任何版权或免责声明（检索无结果）。

建议：无论选哪个方案，先决定项目对"版权内容"的立场，并在文档里写明。如果项目想保持"仅供学习、不提供版权规避能力"的定位，方案 0 或"只做接口、不内置任何渠道、不推荐任何渠道"的方案 1 更稳妥。

## 6. 方案 1 的详细设计要点

**请求协议（项目自定义，不兼容洛雪）**

```
POST {channel.url}
{ "title": "...", "artist": ["..."], "album": "...", "duration": 180, "quality": 320 }
→ { "code": 0, "url": "https://..." }
```

**安全约束**

- 渠道 URL 只来自服务端配置，不来自用户或房间。
- 请求带超时（建议 5 秒）、响应体上限（建议 8KB）、不跟随重定向、校验 `code`。
- 不向渠道发送任何用户信息、Cookie、房间号、IP。
- 渠道返回的链接单独校验：仅 https、禁止内网地址（复用 `isPublicMediaAddress`）、禁止用户名密码与端口。小程序音频代理要求主机在白名单内，渠道链接的主机无法预先枚举，因此需要为"渠道链接"单独设策略：要么只允许网页端直接播放，要么由部署者在配置里声明允许的主机后缀。
- 限流与缓存：结果按 `title+artist+quality` 缓存，短时间内相同歌曲不重复请求；失败做冷却，复用现有 `fallbackCooldown`。
- 日志不记录渠道 URL 的查询参数与令牌。

**行为约束**

- 渠道的结果与原曲的匹配度无法校验，可能出现"换了一首歌"。可返回渠道回报的标题和时长，与原曲用现有 `scoreCandidate` 比对，过低则丢弃。这正是洛雪文档里承认的问题。
- 默认关闭；开启后降级 toast 要明示"已使用备用渠道"。

**测试**

- 渠道响应的解析与业务码校验（fixture）。
- 超时、超大响应、重定向、非法 URL、内网地址被拒。
- 平台失败后回退成功、回退也失败、冷却生效。
- 小程序代理对渠道链接的处理。

## 8. 建议

1. **先确定立场**：项目是否接受提供"绕过平台限制取链"的能力。这决定走哪条路，且需要写进文档。
2. **推荐方案 1，且默认关闭、不内置任何渠道**：只提供"备用取链接口"，由部署者自行配置，实现 issue 里"聚合"的核心诉求，同时不引入沙箱。
3. 不做方案 2：与项目目前"服务端不执行用户代码"的安全模型不一致，风险与收益不匹配。
4. 在 issue 里回复时，说明：可以考虑"服务端可配置的备用取链渠道"，不会支持导入洛雪脚本；并询问用户的真实场景（是想听 VIP 歌曲，还是想要更多来源），再决定是否值得做。

## 10. 若要"完全支持"洛雪：基于源码的分析

"完全支持"的最小定义：导入任意现成的洛雪 `user_api` 脚本，在本项目里能正常取到链接。以下依据洛雪桌面版仓库中的运行时源码（`src/main/modules/userApi/` 的 `preload.js`、`main.ts`、`user-api.html`，以及 `src/common/types/music.d.ts`、`src/renderer/utils/musicSdk/`）整理。

### 10.1 洛雪是怎么隔离脚本的

洛雪桌面版为每个脚本创建一个**独立的 Electron 窗口**：`nodeIntegration: false`、`contextIsolation: true`、`images: false`、`webgl: false`，页面 CSP 为 `default-src 'none'`，拒绝导航、`window.open`、所有权限请求；关闭窗口时清空缓存与存储。脚本通过 `contextBridge` 只能看到 `globalThis.lx`。

这个隔离依赖 Chromium，**在 Node 服务端没有对应物**。脚本拿到的 `lx.request` 是主进程侧的 `needle`，不受 CORS 和 CSP 限制，可以请求任意地址，且没有任何目标过滤。洛雪的信任模型是"脚本在用户自己的机器上运行"，所以对出口没有设防。

### 10.2 洛雪对脚本返回值做了哪些校验

这些是兼容层必须原样复现的行为（`preload.js`）：

| 动作 | 校验 |
|---|---|
| `musicUrl` | 必须是字符串，长度不超过 2048，且匹配 `^https?:`（**允许 http**） |
| `lyric` | 必须含字符串 `lyric`，长度不超过 51200；`tlyric`、`rlyric` 不超过 5120，`lxlyric` 不超过 8192 |
| `pic` | 同 `musicUrl` |
| 外部请求超时 | 默认 60 秒，上限 60 秒 |
| 初始化 | 仅接受 `kw/kg/tx/wy/mg/local`；只取对应源的受支持音质与动作；`inited` 只能发一次 |

注意：洛雪只检查链接"像不像 URL"，**不检查它指向哪里**。本项目的安全策略（仅 https、禁内网、禁端口）比它严，直接复用洛雪的语义会放宽我们的防线。

### 10.3 兼容的真正难点：`musicInfo` 的形状

脚本收到的不是简单的"歌名歌手"，而是洛雪自己的 `musicInfo`，各平台所需字段不同：

| 洛雪源 | 脚本通常依赖的字段 |
|---|---|
| `wy` 网易云 | `meta.songId` |
| `kw` 酷我 | `meta.songId` |
| `kg` 酷狗 | `meta.hash`、`meta.albumAudioId`、`meta.qualitys[].hash` |
| `tx` QQ 音乐 | `meta.strMediaMid`、`meta.id`（songId）、`meta.albumMid` |
| `mg` 咪咕 | `meta.copyrightId`、`meta.lrcUrl / mrcUrl / trcUrl` |

本项目的 `Track` 只有 `source / sourceId / urlId / lyricId / picId` 五个标识字段，三个平台的存法如下（`trackMapping.ts`）：

| 本项目平台 | `urlId` 实际是 | 能否构造洛雪的 `musicInfo` |
|---|---|---|
| 网易云 | 歌曲数字 id | 可以（`songId`） |
| QQ 音乐 | `songmid` | **不完整**：缺 `strMediaMid`、数字 `songId`、`albumMid`；很多脚本取 QQ 链接需要 `strMediaMid` |
| 酷狗 | `hash` | **不完整**：缺 `albumAudioId` 和各音质的 `hash`，脚本无法指定音质 |
| 酷我、咪咕 | 本项目**没有这两个平台** | 无法构造，需要先新增平台 |

结论：**即使只对现有三平台，也要在搜索、入库阶段保存更多平台元数据，才能无损地还原 `musicInfo`**。这意味着 `Track` 要增加一个 `meta` 字段（并同步 `shared/schemas.ts` 的校验、队列持久化、小程序协议）。

### 10.4 音质映射

洛雪的音质是 `128k / 320k / flac / flac24bit`，本项目是 `128 / 192 / 320 / 999`。需要双向映射，且本项目 `192` 在洛雪里没有对应值；`999` 对应 `flac` 还是 `flac24bit` 需要约定。`resolveStreamUrl` 的降级链也要改成按脚本声明的音质集合来走。

### 10.5 要实现的组成部分

| 模块 | 内容 | 难点 |
|---|---|---|
| 沙箱执行器 | 在服务端执行不受信任脚本，隔离、限时、限内存，且可强制终止 | Node 内没有等价于 Electron 窗口的隔离；可选 `isolated-vm`（原生编译）、`quickjs-emscripten`（WASM）、独立子进程加操作系统级限制 |
| `lx` 宿主 API | `on / send / request / EVENT_NAMES / version / env / currentScriptInfo` | `lx.request` 必须走带 SSRF 防护的出口 |
| `lx.utils` | `crypto.aesEncrypt / rsaEncrypt / md5 / randomBytes`、`buffer.from / bufToString`、`zlib.inflate / deflate` | `aesEncrypt` 的 `mode` 直接传给 `createCipheriv`，要限制为白名单；`rsaEncrypt` 使用 `RSA_NO_PADDING`，行为需逐字节对齐 |
| 返回值校验 | 复现 10.2 的全部规则，再叠加本项目更严格的链接策略 | 两套规则的冲突要明确取舍 |
| `musicInfo` 构造 | 见 10.3 | 需要扩展 `Track` |
| 脚本管理 | 导入（本地文件、URL）、头部注释解析、启停、删除、版本与更新提示（`updateAlert`） | 谁有权导入、导入后对全站生效还是房间级 |
| 脚本调用调度 | 并发限制、每次调用超时、熔断、失败冷却、结果缓存 | 一个卡死的脚本不能拖垮房间播放 |
| 音质与动作协商 | 读取 `inited` 声明的 `sources / actions / qualitys` | 映射见 10.4 |
| 歌词与封面（`local` 源专有） | 只有 `local` 源支持 `lyric` 和 `pic` 动作 | 其余源脚本只提供取链，歌词仍用本项目现有来源 |
| 新增平台（若要完整） | 酷我（`kw`）、咪咕（`mg`） | 本项目当前没有，各需要完整的搜索、歌单、歌词、封面实现；见 10.7 |

### 10.6 安全模型：这是与现有架构最大的分歧

| 风险 | 说明 | 缓解（仍不能消除） |
|---|---|---|
| 服务器成为开放代理 | 脚本可以让服务端请求任意 https 或 http 地址，包括内网、云元数据地址 | 复用 `pinnedLookup` 与 `isPublicMediaAddress`；禁止重定向；限制端口；限制响应体大小 |
| 信息外泄 | 脚本能读取传给它的所有数据；若传入用户登录 Cookie，则会被脚本作者拿走 | **绝不传 Cookie**；只传 `musicInfo` |
| 资源耗尽 | 死循环、内存炸弹、大量并发请求 | 沙箱的 CPU 与内存配额、挂钟超时、并发上限 |
| 供应链 | 脚本来源多为社区分发，常被混淆，无法审计，作者可随时发布恶意更新 | 仅允许管理员导入；固定版本哈希；不自动更新 |
| 用户导入权限 | 若允许房间成员导入，等于让任意用户在服务器上执行代码 | 只允许服务端部署者配置，不开放给房间用户 |
| 沙箱逃逸 | V8 isolate 与 WASM 沙箱都有历史漏洞 | 跟进依赖更新；子进程加最小权限；容器内运行 |

关键判断：**洛雪的"用户自己导入、自己负责"模型，不能直接搬到多人共用的服务端**。若坚持完整兼容，必须把导入权收归部署者，等于每个部署者各自承担"执行第三方代码"的风险。

### 10.7 平台覆盖：内置平台是否也要"完全"

洛雪的内置平台是酷我、酷狗、QQ、网易云、咪咕（以及已下线的虾米）。本项目现有三个。

- 对酷狗、QQ、网易云：脚本以 `source` 区分，兼容 10.3 即可。
- 对酷我、咪咕：脚本里 `kw`、`mg` 往往是最常被实现的源，因为它们的链接最容易拿到。**不新增这两个平台，大多数脚本的主要能力就用不上**。这两个平台在本项目中没有搜索、歌单、歌词、封面实现，需要额外的反向工程工作，且这类接口稳定性差（音乐平台接口本身就是不稳定的外部 API）。

### 10.8 工作量与阶段

| 阶段 | 内容 | 粗估 |
|---|---|---|
| 0 | 版权与安全立场决定，写入文档；威胁建模 | 2 到3 天 |
| 1 | 扩展 `Track.meta`：三平台保存洛雪所需字段；schema、持久化、小程序协议同步 | 1 到2 周 |
| 2 | 沙箱执行器与 `lx` 宿主 API、`lx.utils`、受限 `lx.request` | 2 到3 周 |
| 3 | 返回值校验、音质映射、调度（并发、超时、熔断、缓存） | 1 到2 周 |
| 4 | 脚本管理（仅部署者）、配置、日志脱敏、管理界面或配置文件 | 1 周 |
| 5 | 安全评审与对抗测试（SSRF、资源耗尽、沙箱逃逸） | 1 到2 周 |
| 6（可选） | 新增酷我、咪咕平台 | 每个平台 2 到3 周，稳定性无保证 |
| 合计（不含 6） | | 约 6 到10 周，一名熟悉代码库的开发者 |

测试面也会很大：需要一组固定的"伪脚本"夹具，覆盖超时、返回非法值、请求内网、死循环、内存超限等；真实脚本不能进入默认测试套件（会依赖外部服务）。

### 10.9 与"建议"的关系

第 8 节的建议不变：**即使目标是完全兼容，也应该先做方案 1 验证需求**，再决定是否投入 6 到10 周去做兼容层。理由：

1. 兼容层的成本和风险几乎全部来自"执行脚本"这一点，而用户真正需要的只是"取到链接"。方案 1 的 HTTP 渠道可以由第三方把洛雪脚本封装成服务（社区已有大量这类 HTTP 化的洛雪源服务），把沙箱风险放到本项目之外。
2. 若仍要内置，最小闭环是：只支持 `musicUrl`，只支持现有三个平台，只允许部署者通过文件导入，沙箱用独立子进程加容器限制。这样可以把阶段 1 到5 缩到约 4 到6 周，并明确不兼容 `local` 源、不新增酷我咪咕。
3. 无论哪种，**先写下版权与安全立场**，否则兼容层做完也无法安全地发布。

### 10.10 不确定的部分

- 洛雪移动版的运行环境与桌面版不同（文档提到预加载脚本与自定义脚本同环境、内置属性被冻结），本节只分析了桌面版；"完全支持"若要覆盖移动版脚本，还需单独核对。
- `lx.utils.crypto.aesEncrypt` 等函数在真实脚本里的使用方式，我没有抽样分析大量社区脚本，沙箱需要多大的兼容面，需要用真实脚本做兼容性清单后才能确定。
- 工期是按改动范围估的，没有做原型。
